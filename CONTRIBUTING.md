# Contributing

This is a one-person project that is built to be read. Pull requests are reviewed to learn
from them, so optimise for legibility of intent.

## Commits

Conventional Commits, imperative mood, one line, optional short body explaining why.
No trailers, no co-author lines.

```
feat(core): derive offer status from window dates
fix(poll): honour Retry-After before re-queueing a source
docs(adr): record why the table is provisioned, not on-demand
```

## Pull requests

- One concern per PR. Split rather than bundle.
- The description says _why_. The diff already says what.
- Green before you push: `npm run lint && npm run typecheck && npm test && npm run build`.
- A non-obvious decision gets an ADR in `docs/adr/`.
- Prompt changes include before/after numbers from `npm run eval:triage`.
- New GitHub Actions are pinned to a full commit SHA with the version in a trailing comment.

## Opening one

GitHub derives a title and body from the commits only when the branch holds exactly one. With more
it titles the PR after the branch name and leaves this repo's template untouched, which is how a
"Feat/UI polish" with an empty body happens. The "Create a pull request" link git prints after a
push does the same: it only ever shows the empty template. So the description is written before
the push, and one command sends both:

```
npm run pr:draft
npm run pr:open
```

`pr:draft` writes `.git/pr/<branch>.md`: a suggested title on the first line, then the template
with the commit list already under _What changed_. It warns if the branch carries commits the base
already has under another sha, and it will not overwrite a draft that exists. Write the Why, the
Decisions and the Manual steps, and rewrite the title when the branch does more than its first
commit.

`pr:open` pushes the branch and opens the PR with that title and description, or updates the PR if
one is already open, so it is also how a description gets corrected later. It refuses while a
section still holds the template's hint, and while the branch carries commits `main` already has.
`--dry-run` prints what it would do.

`gh pr create --fill` is not a substitute: it writes the commit messages over the body and ignores
the template, so the _why_ never gets written.

## The snapshot commit exception

`apps/web/src/data/snapshot.json` is generated by the publish Lambda and committed straight to
`main` by the project's GitHub App with the message `data: snapshot <timestamp>`. That App is a
bypass actor on the `main` ruleset, which is why its pushes skip the PR and status-check rules.

Nobody else touches that file. A PR that changes it fails the `data-guard` workflow on purpose.
Data changes go through the admin UI or `scripts/admin`.
